# Lecture Notes: Representational State Transfer (REST) APIs

## 1. Introduction to APIs and REST

### What is an API?
An **Application Programming Interface (API)** is a set of rules and protocols that allows one software application to communicate with another. It defines the methods and data formats that applications can use to request and exchange information.

### What is REST?
**REST (Representational State Transfer)** is an architectural style for designing distributed hypermedia systems, introduced by Roy Fielding in his 2000 doctoral dissertation. 
* It is **not** a protocol or a standard, but a set of architectural constraints.
* Web services that conform to the REST architectural style are called **RESTful** web services.
* REST relies heavily on the underlying protocol, which is almost exclusively HTTP in modern web applications.

---

## 2. The Six Architectural Constraints of REST

For an API to be considered truly RESTful, it must adhere to the following constraints:

### 2.1. Client-Server Architecture
* **Principle:** The user interface concerns (client) are separated from the data storage concerns (server).
* **Benefit:** Improves the portability of the user interface across multiple platforms and improves scalability by simplifying the server components.

### 2.2. Statelessness
* **Principle:** Every request from client to server must contain all of the information necessary to understand the request, and cannot take advantage of any stored context on the server.
* **Benefit:** Visibility (easy to monitor single requests), Reliability (easier to recover from partial failures), and Scalability (server does not need to allocate resources to store state between requests).

### 2.3. Cacheability
* **Principle:** Data within a response to a request must be implicitly or explicitly labeled as cacheable or non-cacheable.
* **Benefit:** If a response is cacheable, a client cache is given the right to reuse that response data for later, equivalent requests. This improves network efficiency and reduces latency.

### 2.4. Layered System
* **Principle:** The client cannot ordinarily tell whether it is connected directly to the end server or to an intermediary along the way (e.g., proxies, load balancers, gateways).
* **Benefit:** Enables load balancing, shared caches, and improved security policies without the client knowing the system's complexity.

### 2.5. Uniform Interface
* **Principle:** The fundamental design feature that distinguishes a REST API. It simplifies and decouples the architecture, which enables each part to evolve independently.
* **Four guiding principles of a Uniform Interface:**
    1.  **Identification of resources:** Individual resources are identified in requests, typically using URIs (Uniform Resource Identifiers).
    2.  **Manipulation of resources through representations:** When a client holds a representation of a resource (like JSON or XML), it has enough information to modify or delete the resource.
    3.  **Self-descriptive messages:** Each message includes enough information to describe how to process the message (e.g., `Content-Type: application/json`).
    4.  **Hypermedia as the Engine of Application State (HATEOAS):** Clients should dynamically navigate the API using hypermedia links provided in the responses.

### 2.6. Code on Demand (Optional)
* **Principle:** Servers can temporarily extend or customize the functionality of a client by transferring executable code (e.g., JavaScript).
* **Benefit:** Simplifies clients, but reduces visibility. It is rarely used in modern REST APIs.

## 3. Resources and URIs

In REST, the primary data representation is called a **Resource**. A resource can be a singleton (e.g., a specific user) or a collection (e.g., a list of users).

**Best Practices for URI Naming:**
* Use **nouns**, not verbs (e.g., `/users`, not `/getUsers`).
* Use **plural nouns** for collections (e.g., `/products/123`, not `/product/123`).
* Keep URIs clean and hierarchical to represent relationships:
  * `GET /users/123/orders` (Fetches orders belonging to user 123)
* Avoid file extensions in URIs (e.g., use `/users`, not `/users.json`).

## 4. HTTP Methods (Verbs)

REST APIs map CRUD (Create, Read, Update, Delete) operations to standard HTTP methods.

| HTTP Method | CRUD Operation | Description | Idempotent? |
| :--- | :--- | :--- | :--- |
| `POST` | Create | Creates a new resource in a collection. | No |
| `GET` | Read | Retrieves a representation of a resource. | Yes |
| `PUT` | Update | Replaces an entire resource with a new representation. | Yes |
| `PATCH` | Update | Partially updates an existing resource. | No (usually) |
| `DELETE` | Delete | Deletes a resource. | Yes |

*(Note: An operation is **idempotent** if making multiple identical requests has the same effect on the server as making a single request.)*

## 5. HTTP Status Codes

REST APIs use standard HTTP status codes to communicate the outcome of a request.

* **2xx (Success):**
  * `200 OK`: Standard response for successful HTTP requests.
  * `201 Created`: The request has been fulfilled, resulting in the creation of a new resource (usually returned after a `POST`).
  * `204 No Content`: The server successfully processed the request, but is not returning any content (often used for `DELETE`).

* **4xx (Client Error):**
  * `400 Bad Request`: The server cannot process the request due to a client error (e.g., malformed syntax).
  * `401 Unauthorized`: Authentication is required and has failed or has not yet been provided.
  * `403 Forbidden`: The client does not have access rights to the content.
  * `404 Not Found`: The server can not find the requested resource.
  * `429 Too Many Requests`: The user has sent too many requests in a given amount of time (rate limiting).

* **5xx (Server Error):**
  * `500 Internal Server Error`: A generic error message, given when an unexpected condition was encountered on the server.
  * `503 Service Unavailable`: The server is not ready to handle the request (e.g., down for maintenance).

## 6. Advanced API Design Concepts

### Pagination, Filtering, and Sorting
When querying collections that return a large amount of data, use query parameters:
* **Filtering:** `GET /users?role=admin&active=true`
* **Sorting:** `GET /users?sort=-created_at` (descending order)
* **Pagination:** `GET /users?page=2&limit=50` or `GET /users?cursor=xyz`

### API Versioning
APIs evolve, and changes can break client applications. Versioning is essential:
* **URI Versioning:** `GET /api/v1/users` (Most common and pragmatic)
* **Header Versioning:** Passing a custom header `Accept-Version: v1`

## 7. Example Request & Response

### Request
```http
POST /api/v1/users HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer <token>

{
  "name": "Jane Doe",
  "email": "jane.doe@example.com",
  "role": "instructor"
}
```

### Response
```http
HTTP/1.1 201 Created
Location: /api/v1/users/789
Content-Type: application/json

{
  "id": "789",
  "name": "Jane Doe",
  "email": "jane.doe@example.com",
  "role": "instructor",
  "created_at": "2026-09-10T21:09:16Z",
  "links": {
    "self": "/api/v1/users/789",
    "courses": "/api/v1/users/789/courses"
  }
}
```
*(Notice the `links` object demonstrating HATEOAS principles).*
